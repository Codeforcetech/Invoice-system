# フェーズ6 設計：外部の提出リンク＋請求書のAI取り込み

状態：**6-1・6-2・6-3 は実装済み**（リンクの発行・取り消し、ログインなしの提出、取り下げ・修正・出し直し、メール通知、請求書のAI取り込み）。6-4（見直し）も実施済み（[security-review.md](security-review.md) の追記を参照）。**残るのは、エンジニアによる確認（[engineer-review-checklist.md](engineer-review-checklist.md)）**。

確認事項への回答（顧客）：1. 承認前は取り下げ・修正してよい／2. 既定値（期限30日・承認待ち3件・AI5回）でよい／3. AIへ送ることは同意文言で明示／4. 承認・差戻しはメールで通知／5. URL方式でよい／6. 保存期間の方針はなし。

## 1. 目的（顧客ヒアリングより）

- 初めての先方（業務委託・単発の人）が、メールで送る代わりに、**指定のリンク（フォーム）から請求書と領収書を提出**し、それが管理者の画面に反映される。
- フォーマットがバラバラな請求書（自分で作ったPDFなど）も、**社内の形式に取り込める**。
- 「誰が・いつ・何月分を送ってきたか」が管理でき、承認してから支払管理に反映する（フェーズ5で実装済みの流れを再利用）。

## 2. 全体の流れ

```
管理者：提出リンクを発行（相手ごとに1本。期限・回数の上限つき）→ 相手にリンクを送る
   ↓
相手（ログインなし）：リンクを開く
   A) 請求書のPDF・写真をアップロード → AIが読み取り、入力欄に下書きを入れる → 相手が確認・直して提出
   B) 画面で、請求書をつくって提出（フェーズ5の画面と同じ）
   ↓
提出（承認待ち）→ 管理者の「書類の受け取り状況」に表示、お知らせ
   ↓
管理者：内容と元のファイルを見て、承認（→支払管理に反映）／差戻し（理由つき）
   ↓
差戻し：相手が同じリンクで、理由を見て直して再提出
```

承認から先（支払管理への反映・証憑保存・通知）は、フェーズ5の仕組みをそのまま使う。

## 3. 脅威と対策（最重要）

ログインなしで誰でも到達できる入口になるため、悪用を前提に設計する。

| 脅威 | 対策 |
|---|---|
| リンクの推測・総当たり | トークンは暗号論的乱数（32バイト）。データベースには**ハッシュのみ保存**（元のトークンは発行時に1回だけ表示）。無効・期限切れ・取り消し済みは、**区別のつかない同じ応答（404）**にする。 |
| リンクの流出・転送 | 有効期限（既定30日）、**取り消し**、提出回数の上限。リンクは「1人1本」。画面に事業所の情報は出さない（事業所名と管理者がつけた宛名のみ）。リンクを開いた人は、**そのリンクの提出だけ**が見える。 |
| URLのトークンが、ログやリファラに残る | `Referrer-Policy: no-referrer`、`Cache-Control: no-store`、`noindex`。外部スクリプトを読み込まない。ホスティング側のアクセスログにパスが残る点は、残るリスクとして明記する（必要なら、後述のCookie交換方式に変更）。 |
| スパム・大量送信 | リンクごとの上限（承認待ちは同時3件まで、合計の上限あり）。**IP＋リンク単位のレート制限**（データベースで管理）。見えない入力欄（ハニーポット）。送信サイズの上限（ファイル1つ3MB・10件・1回の送信で合計3.5MB）。 |
| 悪意のあるファイル | 既存の証憑と同じ検査（中身で種類を判定、PDF/JPEG/PNG/WebPのみ）。ダウンロードは `sandbox` つきのCSP、`nosniff`。ウイルス検査は未実装（残るリスクとして明記）。 |
| AI読み取りの悪用（費用・情報漏えい） | AI読み取りは、**有効なリンクがある人だけ**。リンクごとの回数上限（既定5回）と、事業所全体の1日の上限。連続失敗時の一時停止（実装済み）。キーはサーバー側のみ。 |
| 画像内の指示（プロンプトインジェクション） | 読み取り結果は**下書き**にすぎない。値はすべて検証（型・範囲・形式）。相手の確認のあと、**管理者が必ず内容を確認して承認**する。自動で承認・支払いはしない。 |
| なりすまし提出 | リンクは相手に個別に渡す。管理者の画面に「外部リンク経由」「リンクの宛名」を表示。差出人の氏名・登録番号は申告であり、確認済みではない旨を表示（登録番号の実在確認は別途）。 |
| 二重提出・重複 | 同じファイル（ハッシュ）、同じ差出人・月・合計の提出があれば、管理者の画面に警告を出す。 |
| CSRF | 認証用のCookieを使わない（トークンはURL・フォームの値）。サーバー処理はOriginの検査あり。 |
| 監査 | 外部提出の操作も操作ログに記録する（リンクの宛名つき、IPは記録しない方針）。リンクの発行・取り消し・再発行も記録する。 |
| 個人情報 | 外部の人の氏名・住所・振込先・登録番号を保存する。AIへ送ることを、**提出前に同意の文言で明示**する。保存期間と削除の方針は、運用で決める（要確認）。 |

## 4. データ設計（案）

**新規テーブル**

- `SubmissionLink`: `id`, `ownerId`, `createdById`, `label`（宛名・メモ）, `tokenHash`（一意）, `tokenHint`（末尾4文字・識別用）, `expiresAt`, `revokedAt`, `maxSubmissions`, `submissionCount`, `aiReadsLimit`, `aiReadsUsed`, `profile`（前回入力した差出人の情報・JSON、次回の入力補助）, `lastUsedAt`, `createdAt`。
- `PublicThrottle`: `key`（IP＋用途のハッシュ）, `windowStart`, `count`。古い行は定期的に削除。

**変更**

- `Submission`: `submitterId` を**空にできる**ようにし、`linkId`（外部リンク経由か）を追加。差出人は、提出時点の控え（`senderName` など）で表示する（フェーズ5と同じ）。外部提出は、最初から「承認待ち」で作成する。
- `SubmissionEvent.actorId`: 外部の操作は、事業所の管理者をactorにして、`note` に「外部リンク『宛名』から」と記録する（ユーザー行を作らない）。

**採用しない案**：リンクごとに、ログインできないダミーのユーザーを作る方法。ユーザー管理の一覧が汚れ、権限の扱いが複雑になるため。

## 5. 画面（案）

**管理者**（「書類の受け取り状況」から「提出リンク」へ）
- リンクの一覧：宛名、状態（有効／期限切れ／取り消し済み）、提出回数、最後に使われた日時。
- 発行：宛名、有効期限（7日／30日／90日）、提出回数の上限、AI読み取りを使うか。発行直後に**URLを1回だけ表示**（コピー）。送付用の文面のひな形も表示。
- 取り消し、期限の延長、再発行。

**外部の人**（`/s/{token}`、ログインなし、スマホ対応）
- 請求書のPDF・写真をドラッグ＆ドロップ → 読み取り中 → 下書き（編集可）→ 提出。AIが使えない場合は、手入力（実装済みの案内と同じ考え方）。
- 提出後：受付番号と内容の控え。承認前は、同じリンクで**取り下げて直す**ことができる。
- 差戻し：理由を表示し、直して再提出。

**管理者の承認画面**（フェーズ5の画面を拡張）
- 「外部リンク経由」「AIで読み取り」の表示。**元のファイルを横に並べて**確認できる。
- 自動チェックの結果：明細の合計と請求合計が合うか、登録番号の形式、重複の可能性。

## 6. 請求書のAI取り込み（読み取りの仕様）

- 入力：PDF・画像（1つ3MB、最初の数ページ）。モデルは、領収書の読み取りと同じ（既定はHaiku 4.5）。
- 出力（JSON、すべて検証してから画面に入れる）：差出人（名前・住所・登録番号・振込先）、何月分、件名、明細（項目・数量・単価・税率・種類の推定）、請求合計、**金額が税込か税抜か**。
- 変換：相手の請求書が「税込」表記なら、社内形式（税抜＋税区分）に割り戻し、**要確認の印**を付ける。種類（報酬／交通費／経費）は推定で、相手が変更できる。
- 整合性：明細の合計と請求合計が合わなければ、警告を出し、相手に直してもらう（管理者の画面にも出す）。
- 原本は添付として必ず保存する（相手の形式のまま）。読み取れなくても提出は止まらない（手入力）。
- 費用の目安：1件あたり数円程度（領収書より明細が多い分、やや高い）。

## 7. 実装の段階

| 段階 | 内容 | 主な確認 |
|---|---|---|
| 6-1 | リンクの発行・取り消し、ログインなしの提出（手入力）、レート制限、操作ログ、承認画面の「外部リンク経由」表示 | 総当たり・期限・取り消し・上限・他人のデータが見えないこと、をテスト |
| 6-2 | 外部の人による、承認前の取り下げ・修正、差戻しの表示と再提出、送付用の文面 | リンクごとの隔離のテスト |
| 6-3 | 請求書のAI取り込み（読み取り・整合性チェック・同意文言・回数上限・重複警告） | 失敗時の手入力、画像内の指示の無視、費用の上限 |
| 6-4 | 見直し：攻撃の観点のテスト、ログとリファラの確認、資料、（任意）メール通知・Cookie交換方式 | エンジニアによる確認 |

## 8. 残るリスク・未対応（明記する）

- ファイルのウイルス検査はしない。
- 差出人の氏名・登録番号は申告で、実在確認（国税庁の登録の照会）はしない。
- ホスティング側のアクセスログに、リンクのパスが残る可能性がある（URL方式の限界）。
- レート制限はIP単位で、共有IPや攻撃者の分散には限界がある。
- 本番に出す前に、エンジニアによる確認が必要（外部に公開される入口のため）。
- 法令への適合（インボイス、電子帳簿保存法、フリーランス法など）は、この設計では保証しない。

## 9. 確認したいこと

1. 外部の人は、提出後・承認前に、**同じリンクで取り下げ・修正**してよいか（メンバーと同じ扱いにする案）。
2. リンクの既定値：**期限30日、承認待ちは同時3件まで、AI読み取りは5回まで**でよいか。
3. 外部の人の請求書を**AIに送ること**を、提出前の同意文言で明示する形でよいか。
4. 承認・差戻しを、外部の人に**メールで通知する**か（既定は通知せず、管理者がリンクを再送して連絡する。メールを送るには送信サービスの設定とメールアドレスの入力が必要）。
5. リンクの方式は、**URLにトークンを入れる簡易方式**でよいか（ログに残る点が残るリスク）。より安全な「Cookie交換方式」は複雑になる。
6. 外部の人が入力した個人情報（氏名・住所・振込先）の**保存期間**の方針（例：承認・差戻しから◯年、など）。
