# セキュリティレビュー（開発側の自己点検）

実施日 2026-10-04。対象はフェーズ1〜8-4を含む現在のコード。**開発側（AIアシスタント）による静的な点検と、テストでの確認であり、第三者のレビューや侵入テストの代わりにはならない。** 本番へ出す前に、エンジニアによる確認を受けること。

## 点検した範囲と方法

- すべてのサーバーアクション（`actions/`）とAPIルート（`src/app/api/`）で、認証・権限チェックの有無を機械的に洗い出した。
- 認証（セッション、ログイン、パスワード）、公開リンク、ファイルのアップロード・ダウンロード、CSV/PDF出力、SQL、HTMLの埋め込み、ヘッダー、依存パッケージ、リポジトリ内の秘密情報を確認した。
- 事業所（所有者）の境界と権限は、フェーズ7で全アクションに入れ、実アクションを使ったテストで確認している。

## 問題がなかったこと

- 認証のないサーバーアクション・ルート: なし（`getInvoiceByShareToken` は公開リンク用で意図どおり。`saveInvoiceAutosave` と明細取込の各処理は、内部で認証される処理を呼ぶ）。内部ジョブAPI（通知送信）は、32文字以上のシークレットを定数時間比較で確認している。
- SQL: 生のSQLは、会計・ログインのロック用の `pg_advisory_xact_lock`（パラメータ化済み）と、テストの後始末のみ。
- HTMLの直接埋め込み、`eval` は使っていない。
- CSV: 数式として解釈される先頭文字（`= + - @` など）を無効化している。
- ファイル: アップロードは中身の検証をして保存し、ダウンロードは添付ファイルとして返す（`nosniff`、`no-store`、サンドボックスのCSP）。他の事業所のファイルは取得できない。
- 事業所の境界: 全アクションで所有者を固定し、DBの複合外部キーでも守っている。権限の昇格（入力可のユーザーが管理操作をする、など）はテストで拒否を確認。
- セッションのCookie: `httpOnly`、`SameSite=Lax`、本番は`Secure`。
- リポジトリ内に、実際の秘密情報（APIキー、接続文字列）はない。`.env*` は無視されている。

## 残っているリスクと、本番前に決めてほしいこと

優先度の高い順。

1. **IPアドレス単位のレート制限がない（リバースプロキシ／WAFで対応する）。** 上のログイン制限はメールアドレス単位。メールアドレスを変え続ける攻撃は止められない。さらに、パスワード照合に使っている `bcryptjs`（純JavaScript）は、コスト12で**1回に約1秒のCPU**を使うため、失敗するログインを大量に送られるとサーバーが重くなる。プロキシ側でのIP制限と、ネイティブの `bcrypt` または `argon2` への置き換えを検討すること。
2. **パスワード変更・再設定の機能がない。** 利用者は自分のパスワードを変えられず、管理者が作ったパスワードのまま使い続けることになる。セッションはJWT（7日間、サーバー側で無効化できない）で、ログアウトしても盗まれたCookieは期限まで使える。パスワード変更、全端末のログアウト（セッション版番号）、再設定フローが必要。
3. **メールアドレスの大文字小文字の扱い。** ログインは完全一致。保存時に正規化していないため、`A@x.com` と `a@x.com` を別のアカウントとして作れる。保存時とログイン時の正規化と、既存データの整理が必要。
4. **公開の共有リンクの扱い。** 画面からは発行・表示していないが、ルートは残っている。トークンは推測困難（256ビット）だが、失効・期限の仕組みがない。使わないなら、ルートを削除するのが安全。使うなら、失効と期限を足す。
5. **Content-Security-Policyが `frame-ancestors` のみ。** スクリプトの実行元を制限するCSPは未設定（Next.jsのインラインスクリプトにはnonceが必要）。入力値のHTML埋め込みはないが、多層防御として検討する。
6. **Server Actionsをリバースプロキシの背後で動かす場合**、`serverActions.allowedOrigins`（元のホスト名）の設定が必要になることがある。
7. **データベースの権限と暗号化。** アプリは1つのDBロールで接続している。追記専用（操作ログ・履歴）や変更不可（証憑）はDBトリガーで守っているが、DBの所有者権限には効かない。最小権限のロール分離、保存データ（証憑のBYTEAを含む）の暗号化、バックアップの暗号化と復元試験を決める。
8. **エラーメッセージ。** 一部のアクションは、予期しない例外のメッセージをそのまま画面に返す（Prismaの内部エラーは除いている）。本番では詳細を伏せる方針の確認が必要。
9. **証憑・領収書の保存はDB内。** 件数が増えるとDBが大きくなる。外部ストレージ、ウイルススキャンは未対応。
10. **本番向けの設定が未整備。** メール通知の送信（Resendのキー、送信元、アプリのURL、ジョブのシークレット）は未設定で、実送信は未検証。ログの収集、監視、アラートも未設定。

## 確認が必要な環境上の注意

- このフォルダ（`~/Documents/...`）はiCloudで同期されており、ビルド出力に競合コピー（`… 2`）ができて型チェックが失敗することがあった。開発環境は同期の対象外の場所へ移すこと。
- テストは実DBを使う（`RUN_ACCOUNTING_DB_TESTS=1`）。マシンの負荷が非常に高いと、時間制限で不定期に失敗することがある（`--maxWorkers=3` で緩和）。

## 追記：領収書の自動読み取り

- 外部送信: 領収書の画像・PDFを Anthropic のAPIへ送る（キーがある場合のみ）。上流のエラー本文は利用者にもログにも出さない。
- 画像内の文章による指示（プロンプトインジェクション）: システム指示でデータとして扱わせ、返答は項目ごとに検証して、信用できない値（未来の日付、範囲外の金額、一覧にない分類）は捨てる。結果は入力欄の下書きにとどまり、自動で申請しない。
- 費用の使いすぎ: 1人あたり1時間30回の簡易制限（アプリ内メモリ。複数台構成では台数分）。Anthropic側の月上限設定を併用する。
